# M9b — Backups, export and the deployment files: notes

Branch `m9b-backup-export-deploy` (from `main` after PR 12). **Status: built and tested on the development machine. Not run on a real server.** The first real deployment (`docs/DEPLOY.md`) is the test of what could not be tried here: the real domain and certificate, the real bucket (R2 or B2), the real health-check pings and the server hardening commands.
Done when (SPEC M9): the daily backups exist and a restore has been *tried*, the export works, and there is a way to deploy. The first two are proven below; the third is a procedure waiting for its first run.

## What exists
- **Export** (`GET /export`, Settings → "تصدير كل البيانات"): a ZIP with `README.txt` and ten CSV files (customers with balances, categories, products, variants with stock and price, invoices, invoice lines, payments and refunds, returns, return lines, stock movements). UTF-8 with a byte-order mark so Excel reads the Arabic; money in shekels with two decimals; Hebron dates; cancelled and voided rows kept and marked; a text cell that starts with `=`, `+`, `-` or `@` gets an apostrophe so a spreadsheet never runs it. The screen makes the file first and shares or saves it with a second tap (iOS only opens the share sheet straight after a tap), with a fallback that opens it. Each download is audited.
- **`check-books`** (`python -m app.cli check-books`, `services/integrity.py`): 14 rules written from the rows, not borrowed from the code that writes them (lines add up to the subtotal; total = subtotal − discount; discount shares add up; line = qty × price; no invoice without lines; return total = its lines; no line returned more than sold or credited more than worth, exact when all returned; no zero payments; a voided payment has a time; document numbers unique; the sync clock ahead of every row; stock cache = Σ movements; every customer's balance = the formula written again in SQL). Exit code 0/1. Each kind of damage is tested to be found; two kinds (a wrong total, a zero payment) the database itself refuses by its own check constraints, also tested. It also runs inside the random-history QA tests.
- **Sync epoch** (migration `0008`, `after-restore`): `python -m app.cli after-restore` gives the server a new random epoch; every pull carries it. A device that sees a *new* epoch forgets what it had read from the server (rows with `change_seq > 0`; its unsent work, its outbox and its document counters are kept), clears its cursor and reads everything again. Without this, a server restored from an older backup would leave devices believing they had rows that no longer exist and missing new rows numbered below their cursor. Tested on both sides.
- **Deployment files**: `docker-compose.prod.yml` (pinned `postgres:16.4`, Caddy 2.8; only Caddy publishes ports, 80/443; the API runs as an unprivileged user with no capabilities and a health check; log rotation; restart policies), `ops/caddy` (Caddy with the built web app inside, so the server needs no Node; HTTPS for `$DOMAIN` by itself; the client address is rewritten so it can't be forged), the API image now carries `tzdata` (also in `requirements.txt`) and an unprivileged user.
- **Backup service** (`ops/backup`, alpine + restic + the Postgres 16 client): every 4 hours at :15 Hebron time a custom-format dump (checked with `pg_restore --list`) and the pictures go, encrypted, to the bucket; nightly at 03:45 old ones are forgotten (database: 12 newest, 30 daily, 12 monthly; pictures: 7 daily, 4 weekly, 6 monthly) and the repository is checked (deeper on Sundays); pings to healthchecks.io on start, success and failure; the container is "unhealthy" in `docker compose ps` after 8 hours without a success. A repository is created only in a place that says it holds none; wrong keys, a wrong bucket or a wrong password fail loudly instead of making "successful" backups into the wrong place.
- **Restore drill** (`scripts/restore-drill.sh`, `docs/RESTORE.md`): restores the newest backup into a scratch database, runs `check-books` on it, counts the pictures, drops it. And **`scripts/backup-selftest.sh`** runs the whole path on a development machine with the real production images and a local S3 server (`rclone serve s3`) in place of R2.
- **Docs**: `docs/DEPLOY.md` (server, domain, settings, start, proving the backups, daily life, updates, trouble), `docs/RESTORE.md` (the three restore cases, what the iPad does, where secrets live).

## What the self-test proves (and what it found)
Sample books made through the running API → `check-books` clean → first backup (a database snapshot and a picture snapshot) → the stored files do **not** contain a customer's name (encrypted) → a second backup → **the drill passes** → the live books are damaged (stock cache +7), a backup is taken of that, and **the drill fails** naming the damaged variants → a wrong password fails → a wrong bucket fails → pruning applies the retention rules and `restic check` finds no errors.
It found, and these are fixed: the sample-data script needed a plain-HTTP client (the image has no test client); the path of the dump *inside the snapshot* is `/tmp/sales.dump`, not `/sales.dump` (the drill would have failed at the first real use); Git Bash on Windows rewrites `/var/...` arguments (only the development scripts; they now disable it); a failing repository check used to fall through to `restic init`.

## Decisions
- **Every 4 hours, not daily**, plus a nightly prune, on the owner's behalf of the reasoning in the hosting advice: at most about 4 hours of work to re-enter after a total loss. Cost is nothing at this size.
- **restic** rather than `pg_dump | gpg | rclone`: encryption, de-duplication, retention and integrity checks are built in and well known.
- **Pictures are backed up from the server's disk** (restic, incremental). The SPEC said R2 would hold them; they live on a volume, and moving them is not needed to be safe.
- **Image versions are pinned** (`postgres:16.4`, `caddy:2.8-alpine`, `alpine:3.20`, `node:24-alpine`) and raised on purpose; the API image is rebuilt twice a year for the time-zone rules.
- **The drill is a script the owner runs monthly**, not an automatic job: it needs the API image to run the checks, and a green dashboard that nobody has looked at is how backups rot. DEPLOY.md puts it in the monthly routine.

## Not done / known
- **Never run on a real server.** Also never run: the Let's Encrypt certificate, `ufw`/SSH hardening, the unattended-upgrades setup and the provider's own snapshots. They are written as commands in `docs/DEPLOY.md`, to be run and corrected on first use.
- No command to reset the login password (the one user can only be created once); the workaround is in `docs/RESTORE.md`.
- Data written after the last backup and before a total loss is lost (up to ~4 hours); there is no point-in-time recovery.
- No uptime monitor on `/api/health` (UptimeRobot is free: listed in DEPLOY.md).
- Pictures are public by address (unguessable ids); nothing private is stored there.
