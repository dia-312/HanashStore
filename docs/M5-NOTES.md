# M5 — WhatsApp output: notes

Branch `m5-whatsapp` (from `m4-sales`). **Status: built, checked on the PC (tests, WebKit browser journey, PDF rendered in the container) and tried on the real iPad by the user. PR 6, CI green.**
Done when (SPEC section 15): an invoice and a statement are received correctly on WhatsApp from the iPad, online (PDF) and offline (PNG). 

## What exists

- **One layout, two renderers.** `shared/documents.css` is the only stylesheet. The server renders `app/templates/{invoice,statement}.html` (Jinja) to an A4 PDF with WeasyPrint; the device renders `InvoiceDocument` / `StatementDocument` (React, same markup element for element) and turns the page into a 2x PNG with html-to-image. Labels come from `shared/documents_labels.json` on both sides. A test on each side reduces the visible text (tags to spaces, whitespace collapsed) and compares it with `shared/documents_expected_text.json`, so content, order and number formatting cannot drift.
- **Document models are built twice from the same rules** (`app/services/documents.py`, `src/lib/documents.ts`) and both are tested on `shared/documents_cases.json`: header, customer, lines, subtotal, discount (only if more than zero), total, paid now, remaining on this invoice, a "cancelled" stamp with the reason, footer. **No overall customer balance on the invoice.** Money is `₪ 1,250.00`, dates `dd/MM/yyyy HH:mm` in Hebron time, Latin digits, numbers inside `<bdi dir="ltr">`.
- **Statement (كشف حساب)**: opening balance, invoices (debit) and payments (credit) in time order with a running balance; cancelled invoices and voided payments are hidden unless the toggle is on (then struck through, not counted). Default period: the last three months. The server computes forward from the customer's opening balance; the device computes backward from the current effective balance minus what happened since the start of the period, so a period older than the 12 months kept on the device still starts from the right number (the screen says the older rows are not on the device).
- **Business details** (Settings → بيانات المنشأة): name, phone, invoice footer, logo (reuses the image pipeline), and the presentation switch "hide out-of-stock items" that replaces the M4 constant. `GET/PATCH /settings`, `POST /settings/logo` are online only; the settings rows travel in every pull (Dexie v4 `settings`), so the offline PNG has them. Until the client gives his real name, logo and phone the defaults are placeholders (SPEC section 16).
- **Share flow** (`SharePanel`, lazy chunk): _prepare_ then _share_ is two taps, because iOS wants a fresh tap for `navigator.share`. Online and with an invoice the server already has, the PDF button comes first (`GET /invoices/{id}/pdf`, `GET /customers/{id}/statement.pdf`); the PNG button works always. A preview and the file name (`INV-000042.pdf|png`) show before sharing. PNG: fonts embedded, a warm-up render first, and a blank-picture check (the Safari failure seen in the M0 spike) with a message to try again. When `canShare` is false the file opens in a new tab. An invoice or customer still waiting in the outbox only offers the picture and says why. A long statement warns that its picture will be tall.
- Screens: invoice screen has the share panel; `/customers/:id/statement` (lazy) has period fields, the rows, the toggle and the share panel; the customer profile links to it.
- Deployment plumbing: the api image installs pango/harfbuzz and sets `FONTS_DIR` / `SHARED_DIR`; compose (and the e2e stack) mount `apps/web/public/fonts` and `shared/` read-only into the api; CI installs the same packages for the api job.

## Decisions and deviations

- Standalone payments, void and returns stay in M6 and M7; the statement already has the places for them.
- The PNG is exactly as tall as its content (a short invoice is a short picture); the PDF is always an A4 page.
- The device statement never invents rows older than what it keeps; it says so and the PDF from the server has everything.
- New dependencies, all named in SPEC section 3: `weasyprint`, `jinja2` (api), `html-to-image` (web). No `tzdata` was needed.
